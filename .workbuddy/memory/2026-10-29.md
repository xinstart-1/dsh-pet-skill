## 桌面版「改了人设却不生效」的真因（抓包定位）

现象：用户改完人设，桌面版桌宠仍自称「商量 / SensenNova 模型」，人设完全不起作用；无头 CLI 实例却正常。

排查路径（都可复用）：
1. 先排除自身：`/persona` 返回的人设正确、`PUT /config` 生效、删除聊天记忆后仍然失败 → 不是插件缓存/历史问题。
2. 用**鹦鹉判别实验**：人设临时换成「只回复【嘎嘎】」，三条链路（宠物对话 / 抖音 reply-preview / 手动 POST /whisper）分别测 → 桌面三条全挂。
3. **抓包定性**：把 provider 的 `baseURL` 指向本地假 HTTP 服务（打印收到的 JSON），对比两个 profile：
   - 无 `reasoningEfforts` 声明 → `messages[0].role = "system"` ✅
   - 有 `reasoningEfforts` 声明 → `messages[0].role = "developer"` ❌
4. 定位到宿主 pi-ai：`openai-completions.js` 里 `instructionRole = model.reasoning && compat.supportsDeveloperRole ? "developer" : "system"`，而 `resolveModelReasoning` 见 `reasoningEfforts` 就返回 `reasoning: true`。sensenova 的 openai-completions 端点不认 `developer`，于是整段 system 人设被丢弃。

修法与代价：
- **从 provider 配置的模型条目里删掉 `reasoningEfforts`**（已改桌面 profile 的 `cordis.patch.yml`）→ 端到端验证三条链路人设全部生效。
- 代价：DSH 设置里选不了深度思考档位；插件侧 `llm-reasoning.ts` 的 `supportsReasoningOff` 会返回 false，于是不再传 `reasoningEffort:'off'`，模型走默认档（仍会思考，只是不受控）。
- **别用 provider 级 `compat: { supportsDeveloperRole: false }` 绕过**：实测会让 pi-ai 走别的服务商路径，请求根本到不了 `baseURL`（假服务端零请求），且 compatProfile 是全字段必填的 zod 对象，枚举值写错会直接让 provider 不激活。

## 刷抖音改为「推荐」：DOM 路线废弃，改成抓 feed 接口（覆盖上面那条精选实现）

用户一句"改为刷推荐"，把上面的 /jingxuan 精选卡片墙方案整个换掉了。**推荐页是全屏竖滑播放器，和精选完全不同。**

### DOM 路线为什么不干了（一天的时间，全是实测，别再重走）
- `?recommend=1` 有时 302 到 `/jingxuan`，**带 `&from_nav=1` 才稳定停在推荐页**。
- 推荐页一次只播一条：`[data-e2e="feed-active-video"][data-e2e-vid=<awemeId>]`，字段在祖先 `[data-e2e="feed-item"]` 内（`feed-video-nickname` / `video-desc` / `video-player-digg`；时长在文本 `00:13 / 00:29`）。
- **必须限定在活跃项内部取值**：页面预渲染多条，文档级 `querySelector` 拿到的是别的条目（症状：vid 一直在变、作者与描述纹丝不动——第一次就是这么被骗的）。
- 翻页：JS 合成 `KeyboardEvent` 的 `isTrusted=false`，时灵时不灵；**CDP 滚轮完全推不动**；只有 `Input.dispatchKeyEvent`（可信输入）稳。
- 致命：`feed-active-video` 标记**会掉**——标签切后台（`document.hidden` → 视频 paused）或连刷几十条之后它再也不回来，整页读不到 id。重载有时能恢复有时不能，`Page.bringToFront` + 点击都不保证。

### 现在的实现（可靠、快）
- 直接读抖音自己的接口 `**/aweme/v1/web/(tab|module)/feed/**`：一次回 6 条，字段 `aweme_id` / `desc` / `author.nickname` / `statistics.digg_count`（原始数字，如 79199）/ `video.duration`（毫秒，如 348369）。
- 一条 CDP 长连接同时收 `Network.responseReceived` 事件和发命令；`Network.enable` 后按可信方向键让页面取下一批，再 `Network.getResponseBody` 解析 `aweme_list`。首屏那次请求在 enable 之前就发完了，读不到——所以**总会先按一次键**。

## 第三层：让宠物"看画面"（截图取帧，不下载视频）

用户说"这个模型支持看图"，于是把第三层做了。

**关键决定：不下载视频，直接截播放区。**
- 实测 douyinvod 直链对 Node 裸 fetch 回 **403**（要签名/凭据），带 Referer 也不行。
- 视频本来就在浏览器里解码播放 → `Page.captureScreenshot` + `clip` 截播放区，绕过防盗链，也不为看 3 帧付几十 MB。
- **不要用 `video.duration` seek**：抖音流式加载时 `duration` 是 null，`currentTime = duration*0.3` 是 NaN，跳不动（第一次抓到两张一模一样的帧就是这个原因）。改成**自然播放 + 间隔连拍**（默认 3 帧 / 1.8s / scale 0.8，约 25–35KB 一帧）。
- 后台标签里视频是 paused 的：先 `play()` 再截，截完按原状态还原。
- clip 只取高度的 72%（底部压着作者/描述/点赞，文字层已经单独给过）。

**图像怎么进模型**：模型消息收的是**附件引用**（`{attachmentId, mediaType, bytes, width, height}`），不是裸字节。
- `douyin/index.js`：`ctx.get('attachments', false)` 软取 → `service.setAttachments(sink)`（不写进 inject，缺服务时插件照常 apply）。
- `llm.js createHostLlm.generate` 新增 `images` 参数：content 里文本块在前、`{type:'image', attachment}` 在后（与 pet 的 chat.ts 同形状）。
- `service.scanFeed` notify 分支：`feedLookFrames > 0 && attachments && hostLlm` → `web.grabFrames()` → `attachments.saveImages()` → 带图调模型；任一环节不可用就**退回纯文字**（不报错、不假装看了图），返回值带 `frames` 数量。

配置 `behavior.feedLookFrames`（0–6，默认 3，0=只看文案），设置页在「刷会儿抖音」卡里，状态文字显示「刷到 N 条 · 看了 M 帧画面」。

**真机验证**（`.scratch/verify-scanfeed.mjs`，假附件+假模型）：3 帧 25/34/32KB、434×357，帧大小各不相同（证明是不同时刻的画面），模型收到 3 个 image 块。

## UI bug：页面底部被裁 + 保存栏盖住最后一行（`html,body{height:100%}` 惹的）

用户截图圈出设置页底部一块空白，"UI界面有问题"。实测（CDP 量盒子 + 截图）：
- `.content` 被 flex 限制在 660px（视口高），里面内容 1387px，`overflow: visible` → 溢出但不撑大 body，
  于是 `document.body.scrollHeight` = 1482 **小于真实内容底部**。内嵌模式（`?embed=1`）上报的就是这个数，
  父窗口据此设置 iframe 高度 → **iframe 太矮，底部约 70px 被裁**（"生成看看"按钮和卡片底边看不见，只剩一块白）。
- 根因：`html, body { height: 100% }` 把 body 钉成视口高。改成不写死高度、`body { min-height: 100vh }` 后，
  body 随内容长高（1482 → 1572/1553），上报高度正确。
- 第二层：保存栏是 `position: fixed`，内嵌时 iframe 高度 = body.scrollHeight，它贴在**底部**，
  于是又压住最后一行（实测盖住 26px：行 1393–1422，栏 1416–1478）。修法：`body.embed { padding-bottom: 76px }`，
  在 body 末尾给固定栏留位（用 `.content` 的 padding-bottom 不生效——它不算进 body 高度）。

**验收方法（以后照这个来）**：
1. `Emulation.setDeviceMetricsOverride` 把视口设成 `Math.ceil(body.scrollHeight)`，**模拟真实 iframe 高度**；
2. 量目标元素 `getBoundingClientRect()` 与 `.savebar` 的 top，断言 `元素.bottom <= 栏.top`；
3. 截图肉眼复核。
只量普通视口会漏掉第二层问题（普通视口下栏在视口底，量不出 iframe 撑高后的位置）。

脚本：`.scratch/probe-layout.mjs`（高度链）、`.scratch/check-bottom.mjs`（滚到底是否可见）、`.scratch/check-embed-tall.mjs`（内嵌模拟遮挡）。
纯静态文件改动，**刷新即可，不用重启**；测试 145 全过。
