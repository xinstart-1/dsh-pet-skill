## 11:00–11:15 pnpm 故障根因定位 + 发布条件修复

**pnpm EPERM 的真正根因（重要，以后别再猜"缓存残留"）**：本机账户**没有创建符号链接的权限**。
实测：`fs.symlinkSync(target, path, 'dir')` → **EPERM**（`fs.symlink(...,'junction')` 正常）。Windows 上要 `SeCreateSymbolicLinkPrivilege`，普通账户只有开了「开发者模式」才有。
pnpm 的 `forceSymlink`（pnpm.mjs 约 32260 行）逻辑：先试真 symlink → EPERM 由 `createSymlinkAsync` 内部回退 junction → 但注册目录 `projects/<hash>` 已被留下/已存在 → EEXIST → `readlink` 失败 → rename 成 `.ignored_<hash>` → 递归再撞 EEXIST → `renameTried` 分支走 `fs.unlink(目录)` → **EPERM 冒泡**。所以每跑一次就多一个空目录 + 一个 `.ignored_` 空目录，永远好不了。

**可行 workaround（已实测）**：在跑 pnpm 前，手工把 `~/.pnpm/store/v11/projects/<hash>` 建成 junction 指向该 profile 目录，pnpm 立刻正常（`is-odd` 4.3s；本插件 21 包 / 47s）。
- hash 拿法：先跑一次失败的 `dsh plugin add`，错误信息里就有完整路径 `<hash>`。
- 根治：开 Windows 开发者模式（设置 → 隐私和安全性 → 开发者选项 → 开发人员模式），之后 pnpm 走真 symlink 路径。
- 已知 hash：`verify` = `63d34c513d9616023069669370a5e197`、`verify2` = `2136531d2a5b74a17332eefd635e4d04`、`.scratch/pnpm-probe` = `4e173823cf501521b9a707f9b1c2c449`。
